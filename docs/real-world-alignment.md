# 真实车载对齐分析与重构路线

2026-11-11。本文基于公开的车载场景产品形态（理想任务大师、蔚来 / 小鹏智慧场景、MBUX Routines 等）与 SOA 座舱服务架构，对场景工作室 v0.2 做差距分析并给出重构路线。定位不变：保持比赛演示可用，语义向真实车载对齐。本文是决策与路演材料，不是生产协议转换表；所有结论仍以仿真为限，不连接真实车辆，不引入雇主代码、内部接口或真实用户日志。

## 1. 结论摘要

**工程纪律是超前的，领域模型是演示级的。** 证据独立重放、固定基线验证、模型不可信加人工确认、未知结果隔离——这些方法论比许多量产项目的流程更严谨，是项目的差异化资产，应当保留。但与真实座舱场景引擎对照，领域模型有五个结构性差距：DSL 被代码锁死在 20 个固定形状上、触发只有单标量条件、无多场景并发与仲裁、信号无有效性模型、发布链路仅支持午休。

重构方向不是推倒重来，而是让领域模型承载真实语义，同时让既有工程纪律和演示继续成立：

| 分类 | 内容                                                                                       | 处理                                     |
| ---- | ------------------------------------------------------------------------------------------ | ---------------------------------------- |
| 保留 | 人工确认门禁、固定基线验证、证据独立重放、未知结果隔离、停车守卫复查、能力白名单与边界声明 | 不动，作为重构的约束                     |
| 对齐 | 触发与条件模型、场景组合方式、信号与执行语义                                               | 重构为真实车载语义，旧模板迁移为预置实例 |
| 新增 | 多场景调度与仲裁、信号有效性层、车型能力档案、发布签名与回滚、语音意图层                   | 分阶段引入，先概念设计后实现             |

一句话概括：把「20 个固定形状的调参面」升级为「数据驱动的场景规则引擎」，把「单场景仿真」升级为「可仲裁的多场景运行时」，把「nap-only 内存发布」升级为「按车型能力下发的签名场景包」——同时让现有 22 项基线和 Render 演示继续成立。

## 2. 现状盘点：值得保留的设计

以下六项在真实车载语境下依然成立，重构时应作为约束保留。

### 2.1 人工确认门禁（模型不可信）

现状：服务端强制 `confirmed: false`，模型输出经白名单、严格 Schema 与能力依赖校验，所有草案须人工核对差异后确认；运行时只处理类型化动作，不执行模型产生的代码（`server/provider.ts`、`src/domain/scenario.ts`）。

真实依据：量产座舱的场景上线要经过需求评审与发布审核，LLM 生成内容不能直接成为车端可执行配置。「模型是不可信数据源、不直接控车」是行业共识，本项目的门禁与之同构。

保留方式：重构后编译链路不变，通用 DSL 仍经同一校验与确认门禁；模型可组合的范围扩大，但确认与校验强度不降。

### 2.2 固定基线验证

现状：预期来自未修改的模板基线，被测版本不能改写期望（`src/domain/verification.ts:59-60`）；284 项用例覆盖 20 个模板，版本对照按固定用例 ID 对齐新增失败与恢复通过（`src/domain/comparison.ts`）。

真实依据：对应真实测试用例库独立于实现版本——改参数不会让测试自动改预期，这是回归测试可信的前提。许多项目的测试随实现漂移，本项目刻意避免了这一点。

保留方式：模板迁移为预置实例后，基线仍固定于预置实例的产品预期；自定义场景合理偏离基线时报告为失败，需另行建立新基线的纪律不变。

### 2.3 证据独立重放

现状：导入证据在独立实例重放，比对事件、终态、状态、进度与接管锁；`runtimeVersion 1.9.0` 兼容 1.0.0–1.8.0 旧记录（`src/domain/evidence.ts`）。

真实依据：对应 HIL 与日志回放回归——用记录的输入重建运行并核对输出一致性。项目明确「重放一致不等于动作成功，也不能证明来源或防止同时篡改输入与结果」，这一边界声明诚实且必要。

保留方式：运行时语义升级时延续版本化重放，新增 runtimeVersion 并保留旧版本语义分支，旧证据仍可回放。

### 2.4 未知结果隔离，不自动重试

现状：回读丢失记为 `unknown`，停止同设备后续控制，终态 `uncertain`，保留最后已知状态，不推断动作未执行（`src/domain/runtime.ts`）。

真实依据：执行器状态未知时盲目重试可能造成重复动作或掩盖故障。真实车控在反馈缺失时进入安全状态并等待人工或诊断介入，而非假设成功或失败。本项目的处理与功能安全的 fail-safe 思路一致。

保留方式：仲裁层引入后，unknown 资源仍隔离，且应从「单运行内隔离」升级为「跨场景生效」——一个场景触发的未知状态应阻止其他场景继续控制同一资源。

### 2.5 停车守卫逐动作复查

现状：每个动作发送与回读前复查 P 挡且车速 0；座椅复查占用，车窗复查窗路（`src/domain/runtime.ts`）。

真实依据：前置条件在请求时与执行时分别校验是车控服务的标准做法——条件可能在请求排队期间失效。逐动作复查而非一次性检查，正是真实执行层的行为。

保留方式：守卫从「全局停车」扩展为「按能力声明的前置条件」，复查时机不变。需说明：真实车辆允许部分行驶中自动化（如空调调节），本原型限定停车是明确的范围声明而非缺陷；重构后可按能力开放行驶中控制，但需配套分心与安全管理。

### 2.6 能力白名单与边界声明

现状：能力目录 13 项各带 `boundary` 字段；`docs/local-optimization.md` 列出接入前需核实项——音量百分比不等于设备音量级、开关能力不等于调光能力、角度不代表实车行程或防夹。

真实依据：对应真实能力目录与服务契约——每项能力有参数语义、单位、区域、反馈与接入边界。「不能仅因名称相近就认为能力兼容」是集成纪律，本项目已将其制度化。

保留方式：能力目录升级为车型能力档案的基础，`boundary` 字段延续为集成核实清单；新增能力必须先声明边界再接入。

## 3. 差距分析：对照真实车载场景工程

对照对象为公开产品形态（理想任务大师、蔚来 / 小鹏智慧场景、MBUX Routines）与 SOA 座舱服务架构。每条按「现状 → 真实做法 → 影响」展开，按对产品愿景的影响排序。

### 3.1 触发与条件模型

现状：

- 触发是单个扁平对象：11 种信号、操作符仅 `gt / lt / gte`、阈值加持续秒数（`src/domain/scenario.ts:77-101`）。没有 AND/OR/NOT，没有条件列表或嵌套表达式。
- 没有墙上时钟与日历：`elapsedSeconds` 是「自预演开始起的秒数」（`src/domain/runtime.ts:467`），三个预约模板是相对定时器，不是「每天早上 8 点」。
- 没有真实地理围栏：`pickupDistance` / `homeDistance` 是用户注入的标量距离；到家还硬编码「先观察到范围外」的边缘守卫（`src/domain/runtime.ts:468-473`）。没有坐标、没有进出事件。
- 没有用户身份与驾驶员档案：占用只是布尔，无手机钥匙、人脸或账号。
- 车门 / 安全带 / 充电不是第一类触发器：完全没有安全带信号；车门状态是硬编码离车状态机的输入（`src/domain/runtime.ts:445-461`）；充电是运行时守卫，不是触发信号。

真实做法：任务大师、智慧场景等支持多条件组合（时间 + 位置 + 车辆状态 + 天气）、事件触发（车门开闭、插枪、挡位、安全带）、日程（墙上时钟加重复规则）、地理围栏进出、用户身份（手机钥匙 / 人脸识别驾驶员并载入个人档案）。条件可 AND/OR 嵌套，动作可带延迟与顺序。

影响：无法表达「工作日早 8 点、识别到驾驶员、车外温度低于 5°C 时预热座舱并开座椅加热」这类真实高频需求；「预约」与用户心智中的绝对时间不符。这是「从一句需求到场景」的愿景与实际表达力之间的第一道差距。

### 3.2 场景组合与扩展性

现状：

- `validateScenario` 把每个 templateId 锁死到固定触发 / 提醒组合（`src/domain/scenario.ts:317-395`）：nap 必须 wake、charging 必须 charge 加 batteryPercent、四个雨天场景必须 rainLevel gt、passengerWait 与 driverExit 双向绑定。
- 新增一个场景族至少要协同修改四处：scenario.ts（枚举加校验）、templates.ts、verification.ts（新分支）、runtime.ts（预览状态 / 版本门）。
- 运行时硬编码模板分支：`previewVehicle` 按模板合成初始状态（`src/domain/runtime.ts:221-290`）；关窗结果提醒由 `hasWindowResultReminder` 注入（`src/domain/scenario.ts:125-130`），不在 DSL 中表达。
- 编译器是关键词 / 正则匹配而非解析（`src/domain/compiler.ts`）；模型只能在 20 个形状内调参。

真实做法：真实场景引擎是数据驱动的规则引擎——条件、动作、策略是可自由组合的数据，新场景等于新数据而非新代码。模板是预置实例，不是类型锁。

影响：「自然语言编排」目前实际是「自然语言调参」。模型不能组合新场景，只能在固定形状内改参数。这是与产品愿景差距最大的一条，也是扩展成本高的根因。

### 3.3 并发与仲裁

现状：

- 单运行时单场景：`src/App.tsx:174` 持有一个 CabinRuntime；车端在运行未终态时拒绝启动新包（`src/components/MyScenes.tsx:104`）。
- 手动接管锁运行期永久：`applyManual` 把整个资源组加入 locked（`src/domain/runtime.ts:901`），不释放、无超时、无交还。
- 无跨场景仲裁：没有调度器、优先级、抢占或排队。唯一的冲突处理是单运行内的手动对自动化。

真实做法：真实车上多场景共存，并与 OEM 内置功能（自动空调、自动雨刮、迎宾 / 离车模式）竞争同一执行器。需要优先级仲裁层（安全 > 手动 > OEM 默认 > 用户场景）、按资源仲裁、接管交还（一段时间无手动操作或下次触发时释放，而非永久）。

影响：「雨天关窗」与「午休」不能共存；手动调节后自动化永久让出（真实车会在无操作一段时间后交还）。这是真实座舱场景引擎的核心工程问题，当前完全缺失。`docs/local-optimization.md` 已自认「多场景仲裁尚未实现」。

### 3.4 信号与执行层

现状：

- 无信号有效性 / 新鲜度 / 时间戳：信号是 zod 有界数值，经 `setSignals` 即时生效；「未知」只是可选字段的 undefined，仅部分守卫保守处理。
- 固定 1 秒回读：正常路径在接受后恰好 1 tick 确认（`src/domain/runtime.ts:809-813`）；`timeoutSeconds` 只在故障注入时起作用。无按能力时延、无抖动。
- 瞬时执行：`apply()` 是字段赋值，座椅角度一步到位，无执行器行程；空调动作不改变舱温（舱温只由用户注入）。
- 单区空调、单一电源；每次运行仅一个故障，来自固定三类变体（`src/domain/runtime.ts:89-95`），无组合、间歇或部分故障。

真实做法：CAN / SOME-IP 信号有 SNA / 无效值、不同更新率与网关时延；请求与回读需关联；执行器有行程（座椅 / 车窗）；空调分区；信号新鲜度是安全前置条件。接入层通常以 VSS（COVESA Vehicle Signal Specification）风格的信号抽象隔离车型差异。

影响：仿真结论不能外推到实车时序行为。`docs/local-optimization.md` 已列出五项未实现：信号新鲜度、真实回调注入、服务断连、多场景仲裁、设备桥接。

### 3.5 发布与车端

现状：

- 发布仅 nap：`isInstallableNap` 与包 Schema 把 sceneId 锁为 nap（`src/domain/scene-package.ts:18-29`）；发布门禁要求唤醒加完整恢复的重放通过（`napRestored`）。
- 内存单租户：published / installed 存于服务进程内存，重启清空；Render 上所有访问者共享一台模拟车端。无持久化、无签名、无按车下发、无回滚。
- 语音是正则：`voiceNapMinutes` 匹配「开始午休 N 分钟」（`src/domain/scene-package.ts:67-76`），无 ASR / NLU；车端运行时与工作室是同一个浏览器侧仿真器，没有独立车端执行环境。

真实做法：发布链路需要车型能力档案（按 Trim 裁剪——座椅通风仅高配、阅读灯仅开关）、包签名与完整性校验、按车下发、灰度与回滚、多租户隔离。语音经 ASR / NLU 做意图解析与参数提取，并受行驶中分心规则约束。

影响：发布链路是演示道具而非交付架构。nap-only 意味着「发布带版本的场景包」这一产品承诺只对一个场景成立。
